# 引用 bbox 粒度评估：块级 / 单元格级 / 字符级

- 日期：2026-11-03
- 背景：页图高亮已落地为**块级**（见 `docs/design.md` §9）。本文评估是否值得做到
  单元格级或字符级，给出数据与结论。
- 结论：**维持块级**。单元格级/字符级在当前 OCR 能力下成本高、可信度不升反降。

## 1. 当前能力与数据来源

| 引擎 | bbox 来源 | 粒度 | 单位 |
|---|---|---|---|
| VLM（openai 兼容） | `ocr.json` 的 `blocks[].bbox` | 每个**文本块/表格块**一个矩形 | 页图像素 |
| fixture | 同上（合成件） | 块级；且**多数为 null** | 像素 |
| 文本层（PyMuPDF） | `get_text("dict")` 行框合并成块 | 块级（按行聚簇，接近行组） | PDF 点 |

装载时统一归一化成 0~1 比例坐标（`pipeline._page_bbox_normalizer`），前端
`viewBox="0 0 1 1"` 覆盖，缩放/缩略图不重算。

实测（`data/derived` 真实扫件，2315×3274 页图）：`gbt1568` 每个 chunk 都能拿到 1~N 个
块框；`demo_scan`（fixture）全为 null。所以"有没有框"取决于引擎是否返回 bbox，
不是渲染端能力。

## 2. 单元格级（表格）

- **当前拿不到单元格坐标**：VLM 只给一个覆盖整张表的块 bbox（`parse_html_table`
  重建的是单元格**文本网格**，没有每格的像素坐标）。因此 `[p.4 §表 1]` 只能框住整表。
- **要做到单元格级**，需要 OCR 引擎返回**每个单元格的 bbox**（如 PP-Structure /
  TableBank 系模型的 cell 检测），并让 `TableGrid.CellSpan` 带上坐标、再与
  `n_rows/n_cols` 对齐。成本：换/加一个表格结构引擎、处理合并单元格坐标系、回归
  大量表格用例；且当前表格已有 `parse_degraded` 降级路径，叠加坐标只会扩大面。
- **可信度收益存疑**：扫描件表格常有合并单元格、跨页续表、倾斜，cell bbox 误差
  可能比"整表框"更误导（读者会以为"就这一格"，实际框歪了）。整表框至少永远
  正确包含答案。

结论：**不做**。整表框 + 表格原文足够定位。

## 3. 字符级（words / chars）

- 需要 **word/char 级检测框**（PaddleOCR、Tesseract、或云端 OCR 的 word bbox）。
  这不是"多写点前端代码"，而是**更换/新增 OCR 能力**。
- 代价：新依赖（体积、许可证、部署复杂度，与"三条命令可复现""依赖尽可能少"
  冲突）；真实扫件上 char bbox 抖动大；还要重新过一遍跨引擎一致性校验。
- 收益：把"块区域"缩到"这几个字"。对**核对方便度**有小幅提升，但**不改变答案
  是否正确**——而本项目的重心是"答案可被核验"，块级已满足。

结论：**不做**；作为未来若引入 word-level OCR 时的自然延伸。

## 4. 结论

| 粒度 | 现在 | 建议 | 理由 |
|---|---|---|---|
| 块级 | ✅ 已有 | **保持** | 每个 OCR 块一个框，语义正确、成本为零 |
| 单元格级 | ✗ | 不做 | OCR 不返回 cell bbox；换引擎成本高、可靠性存疑 |
| 字符级 | ✗ | 不做 | 需 word-level OCR；收益小、依赖与噪声代价大 |

若将来引入 word-level 引擎，可把 `Chunk.bboxes` 从"块框"扩展成"词框列表"，
前端 `BBoxLayer` 不需要改（仍是一组 `rect`）——数据形状已经兼容更细粒度。
