# 迁移到不同业务场景

作业明确要考"方案能否迁移到金融、合规、客户交付"。本文说明：
**哪些是改配置、哪些要改代码、哪些是真正的难点。**

一句话结论：**结构性的差异用 `config/domains/*.yaml` 吸收，语义性的差异必须改代码，
而真正的成本不在技术，在验收标准与人工复核流程。**

---

## 一、迁移的三个层次

| 层次 | 手段 | 典型工作量 |
|---|---|---|
| **① 配置级** | 新增一个 `config/domains/<name>.yaml` | 半小时 |
| **② 适配级** | 新增一个 OCR/LLM 引擎适配器 | 半天 |
| **③ 流程级** | 改评估集、验收阈值、人工复核环节 | 数天～数周 |

**大多数团队低估的是第 ③ 层。** 换一份文档，技术上一小时能跑通；
但"这份文档答到什么程度算合格"这个问题，每换一个行业都要重新回答一次。

---

## 二、配置级迁移：五类场景的现成 profile

仓库已内置五个 profile，改的是这些参数：

| 参数 | 作用 | 为什么因场景而异 |
|---|---|---|
| `clause_patterns` | 条款号正则 | 国标是 `3.1.1`，公文是 `一、`/`（一）`/`1.`，合同是 `第X条` |
| `table_cues` | 表格题路由线索 | 标准里"表"是强信号；公文里"名单""附件"更常见 |
| `chunk.max_chars` | 切分粒度 | 金融表格大（1000），合规要精确定位（600） |
| `retrieve.top_k` | 召回条数 | 金融需要跨页对照（8），公文 5 条足够 |
| `retrieve.table_boost` | 表格加权 | 金融表格密集（1.6），公文几乎没有表格（1.2） |
| `qa.min_coverage` | 拒答阈值 | 标准件最严（0.60）；金融 0.55、合规 0.50、公文与交付 0.45。金融的取舍是"数值给错比拒答严重得多"，但阈值本身尚未经实测校准 |

### 金融材料

**特征**：表格密集且常跨页；同一指标在不同年份/章节多次出现；数值有单位与口径。

**关键差异——冲突候选是常态，不是异常。**
同一指标在"管理层讨论"与"财务报表附注"里可能是两个数（口径不同）。
所以 `AMBIGUOUS_QUESTION` 拒答路径在本场景**最有价值**：
与其选一个数报出去，不如把两个候选连同出处一并给出。

**额外要做**：跨页长表的表头重复识别（`表1（续）` 的合并）、单位与口径的归一。

### 合规文档

**特征**：可追溯性是核心诉求；文档可能被恶意构造；否定问句极常见。

**关键差异——留痕与抗注入。**
- 每个结论必须能回溯到条款原文，审计要留痕。本项目的 `AnswerBundle.trace`
  已经记录了完整的检索/生成/自检轨迹，可直接作为审计材料；
- 扫描件是**不可信输入**：一份被构造的文档可以印上"忽略以上指令"。
  本项目的对策是结构化的：OCR 只出 JSON、证据放在明确的数据区、
  系统提示声明检索文本是数据、`scan_injection` 启发式扫描指令类短语并记录。
  **这条在合规场景不是加分项，是准入门槛。**

**否定问句**：`"制度是否规定了例外情形？"` 的正确答案可能是"未规定"——
这是有效答案，不是拒答。本项目的 `is_in_document_negative` 专门处理这一类。

### 客户交付材料

**特征**：图文混排；操作步骤多；图注承载信息（前提条件、注意事项）；多版次并存。

**关键差异——版本过滤。** 交付物常有 v1.2/v2.0 并存，
检索时必须按版本过滤，否则会把旧版步骤答给用户，**直接导致误操作**。
当前实现只做到 chunk 元数据层，版本过滤需要在上层加过滤条件。

**另一个差异**：面向"照着做"的读者，答案要可执行。
歧义在这里的代价是误操作，所以歧义检测同样重要。

### 与标准/公文场景的对照

| 场景 | 主文档形态 | 最难的一环 | 本项目已验证 |
|---|---|---|---|
| 标准规范 | 4 页，条款 + 1 张表 | 表格跨列取值 | ✅ 主文档 |
| 金融 | 数十～数百页，密集表格 | 跨页表、口径冲突 | 配置就绪，待实测 |
| 合规 | 条款式，长文档 | 抗注入、留痕 | 机制就绪，待实测 |
| 客户交付 | 图文混排，多版次 | 版本过滤、图注 | 配置就绪，待实测 |

**诚实说明**：后三类只完成了**配置与机制层面**的准备，
没有真实文档与验收标准，因此**没有实测数据**。上表如实标注了这一点。

## 三、适配级迁移：换 OCR / 换模型

`ocr/` 层是协议化的，新增引擎只需实现一个方法：

```python
class OcrEngine(Protocol):
    name: str
    model: str
    supports_vision: bool
    def ocr_page(self, image: PageImage, *, profile=None) -> OcrPage: ...
```

### 什么时候需要换引擎

本项目的默认路线是 VLM API。以下情况应当换：

| 情况 | 建议 | 理由 |
|---|---|---|
| 数据不能出内网 | 接本地引擎（RapidOCR + RapidTable） | 纯 ONNX、无 GPU、无外部依赖 |
| 表格精度要求极高 | 专用文档模型（PaddleOCR-VL / GLM-OCR 等） | 实测在中文表格上显著优于通用大模型 |
| 需要对表格做确定性校验 | 加 RapidTable 做第二引擎 | 跨引擎比对需要两个独立来源 |
| 成本敏感、量大 | 批处理 + 专用 OCR 模型 | 专用模型单价远低于通用 VLM |

**注册表已经预留了 `local` 位**，`ingest` 不需要任何改动。

> **Python 版本已为此钉在 3.12**：MinerU 在 Windows 上只支持 3.10–3.12
> （被 `ray` 卡在 3.13），EasyOCR 也不推荐 3.12+。
> 钉在这里 = 本地引擎的备选路线全部保留。

### 换生成模型

`llm/` 层同样是协议化的，已内置 OpenAI 兼容与 Anthropic 两个适配器。
换供应商只需改 `.env` 里三个变量。**没有配置生成模型时会自动降级为抽取式回答**，
检索、引用、自检、拒答全部照常工作。

## 四、流程级迁移：真正的成本在这里

### 每个场景都要重新回答的问题

1. **什么算答对了？** 标准件的答案是精确数值（1.0 就是 1.0，1.5 就是错）；
   合规件的答案可能是一段论述，允许不同措辞。**判分口径完全不同。**
2. **拒答阈值定在哪？** 金融要宁可多拒（`min_coverage: 0.55`，见 `config/domains/finance.yaml`），
   客服场景要宁可多答（低阈值 + 人工兜底）。
3. **哪些字段必须人工复核？** 本项目的噪声实验就是为了回答这个：
   当证据被污染时系统会自信地答错，所以**高风险数值字段应当有复核环节**。
4. **合规与审计要求是什么？** 数据能否出内网、日志留多久、是否需要逐条留痕。

### 建议的迁移步骤

```
1. 拿 10~20 份真实文档 → 跑 detect 与 ingest，看解析质量
2. 人工校对 2~3 页 → 算 CER，确认是否达到该行业的验收线
3. 从真实业务问题里取 15~20 题 → 写金标集（含无答案题与否定题）
4. 跑 eval → 看分题型准确率与拒答表现，而不是只看总分
5. 按结果校准 min_coverage 与 top_k，再跑一次
6. 把 eval 设为 CI 门禁，之后每次改动都跑
```

第 3 步是最容易被跳过、也最不能跳过的一步：**没有金标集，后面所有数字都无从解释。**

## 五、已知的规模瓶颈

| 瓶颈 | 现状 | 规模化时要做什么 |
|---|---|---|
| 索引在内存 | 适合数百 chunk | 上千页需换向量库或磁盘索引 |
| BM25 每次查询全量打分 | 同上 | 需要倒排索引 |
| 无并发控制 | 逐页串行识别 | 换异步 + 限流；注意退避抖动（已实现） |
| 缓存以单文件存储 | 适合小规模 | 换键值库 |
| 无版本过滤 | chunk 元数据已具备 | 上层加过滤条件 |

这些在作业规模下都不是问题，但**在金融/合规的真实体量下会成为问题**，
所以列在这里而不是假装不存在。

---

### 多文档检索：现在支持到什么程度

金融与合规场景的问题很少只落在一份文件上——"这几份制度对留存期限的规定
是否一致"、"合同和技术协议对验收标准各是怎么写的"，
都需要**跨文档**检索。`docqa ask --doc A --doc B` 已经支持，
合并时做了三件事，每一件都有对应的坑：

| 做法 | 为什么 |
|---|---|
| 片段直接拼接 | `chunk_id` 本身带 doc_id 前缀（`<doc_id>:p1:c5`），不会冲突，引用也能看出答案来自哪份文件 |
| **重建**索引，而不是合并分数 | BM25 的 IDF 依赖整个语料，各自建好再合并分数**不可比** |
| 失败页升级成 `(doc_id, page_no)` | 两份文件的"第 3 页"是两回事。原先按页码裸比，A 的失败页会让 B 的证据**误拒答**——误拒答不危险，但会毁掉拒答的可信度 |

**还没有做的**：

- **跨文档的关系推理**（"哪份文件更新"、"两份是否冲突"）。现在的多文档
  只是"一个更大的语料"，答案仍然来自单一文档的片段；
  真正的冲突检测需要先把两份文档的对应条款**对齐**，那是另一个模块。
- **文档级过滤与排序**（"只在 2024 版里找"）。`Chunk` 上已有 `doc_id`
  等元数据，但检索层还没有过滤条件。
- **增量更新**。改一份文档要整个重建索引——现在规模下无所谓，
  上千份时要改成增量。
